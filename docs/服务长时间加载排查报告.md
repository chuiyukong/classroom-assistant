# 服务长时间加载排查报告 · 1.9.0

2026-09-12。依据源码、受控故障复现和本机浏览器测试；未取得教室故障现场日志，以下是相对可能性排序，不是已确认的现场根因。

## 1. 最可能原因与证据

| 排序 | 判断 | 源码位置（1.9.0）与证据 |
|---|---|---|
| 高 | **空闲长连接叠加轮询，触及旧版150条连接上限**，Waitress停止接收新连接；刷新会增加竞争 | `launcher.py:82`。旧值12线程/150连接/30秒空闲；独立复现占住149条连接后，新增无数据库的health请求也超时。新配置64页面持续测试观察到261条连接，说明150明显偏紧。连接数不是线程数，空闲连接也占额度。 |
| 中高，放大因素 | 多路轮询持续施压，断线后同步重试；选座页聚焦刷新、模块上下文查询没有防重入 | `classroom/web/static/app.js:107`、`modules.js:125`及`:140`、`student-rollcall.js:9`。旧考勤页面1秒考勤、3秒座位上下文、0.7秒点名，64页面理论约177请求/秒，尚不含静态资源和教师操作。点名发生的5秒内还重复读取完整名单。 |
| 中，需现场日志 | **写锁等待占满12个工作线程，其他请求排队**；慢磁盘、杀毒扫描、外部数据库工具写事务可能触发或放大 | `classroom/core/db.py:178`：15秒busy_timeout、写BEGIN IMMEDIATE；`:207`启用WAL。受控外部写锁下，12个写请求全部等待时health确实排队，释放锁后恢复。JS超时12秒短于数据库等待15秒，浏览器放弃请求不等于服务器工作立即取消。普通读请求使用BEGIN，WAL允许读写并行；没有发现日常读取一律拿写锁或明显连接未关闭的问题。 |
| 中低，但不能排除 | 服务循环退出，启动窗口仍存在；或教师机磁盘/CPU/内存压力、系统休眠 | `launcher.py:87`和`:134`。旧版daemon线程异常没有传递给窗口，固定“运行”字样不能证明HTTP可用。Waitress通常捕获单个任务异常，不代表整个循环必定不会退出。新增监督和线程快照。 |
| 取决于现场 | IP变化、地址选错、无线拥塞/客户端隔离、防火墙或安全软件、代理、极域批量打开造成突发 | `launcher.py:19`地址检测、`:81`绑定所有IPv4接口。若教师127.0.0.1也卡，单纯LAN因素的解释力下降；如果本机health快而学生机慢，优先查网络。当前没有网络现场证据。 |

两个同名EXE进程通常是PyInstaller单文件父进程解压/清理加运行子进程，**不等于两个服务**；应用还有同一数据目录单实例锁（`launcher.py:31`）。不同数据目录可以各自运行，端口冲突会报错。单文件解压及杀毒可能拖慢启动，但不能仅凭两个进程解释运行中卡顿。[PyInstaller运行说明](https://pyinstaller.org/en/stable/operating-mode.html)

用户也报告单独教师使用仍卡顿，这一点不能只用“60台学生机并发”解释；须检查是否仍有后台浏览器连接、外部写锁、磁盘/安全软件影响或服务循环异常。重启后短时未恢复也不证明SQLite一直锁死，可能叠加浏览器重连、启动解压或系统负载。

没有证据表明进程优先级是主因，暂不修改优先级。应先用任务管理器确认CPU、内存、磁盘是否持续饱和，以及具体哪个PID在监听端口。提高优先级不能解除连接上限或SQLite锁等待。

Waitress连接限制、空闲清理和任务队列机制参见[参数说明](https://docs.pylonsproject.org/projects/waitress/en/latest/arguments.html)与[设计说明](https://docs.pylonsproject.org/projects/waitress/en/latest/design.html)。本项目实际验证版本为Waitress 3.0.2。

## 2. 已做的修正

- Waitress保留12个工作线程；连接额度150→400，空闲超时30→10秒，清理周期5秒。400为Windows select文件描述符上限留余量，不能任意改为几千。提高连接数不意味着解决所有慢查询。
- 选座轮询和上下文查询防重入；轮询失败逐步退避、增加随机错峰。点名通知成功查询间隔约1.4—2.1秒；无通知不查数据库，有通知仅查当前上下文与设备对应学生，不再反复构造完整名单（`classroom/rollcall/service.py:96`）。弱网可能错过原有5秒临时通知，未改为历史消息保存。
- 数据库连接设置异常时也确保关闭；保留15秒锁等待及事务边界，新增等待记录，未盲目缩短可能影响登记成功的事务超时。**长时间外部写锁仍可能造成排队，尚未通过现场日志定位持锁来源。**
- 服务循环退出记录日志，窗口实时显示“服务正常 / 响应缓慢 / 已停止”，不再靠静态文字判断。
- 初次数据未加载时，课堂操作按钮先禁用，避免加载途中点击无效。

## 3. 旧日志不足与新增诊断

旧`application.log`主要记录Flask异常，约1MB×4份，正常请求、连接上限、Waitress队列、SQLite等待、进程关系、线程存活没有连续记录。无控制台EXE中Waitress自己的警告也不能依赖用户看到。

新增同一数据目录的`diagnostics.jsonl`，INFO级别，2MB×5份滚动，慢事件每秒最多5条，其余累计计数。实现入口`classroom/core/diagnostics.py:18`。

| 内容 | 用途 |
|---|---|
| 启动：版本、PID/父PID、打包状态、Python/SQLite/系统版本、监听端口、线程/连接设置、局域网IPv4地址 | 判断运行的是哪个版本、哪个进程、哪个地址 |
| 每约5秒：服务线程存活、127.0.0.1健康探测（2秒超时）、连接数、活跃线程/队列数、Flask在途请求与最长耗时、响应码汇总、数据库读写/等待/错误计数、累计CPU时间、DB/WAL文件大小 | 区分连接饱和、工作线程排队、慢业务与服务退出；探测超时时周期会延长 |
| 请求≥500ms或5xx：请求编号、路由模板、方法、耗时、状态码 | 定位慢接口；响应头X-Request-ID便于对应。此耗时从进入Flask开始，**不含进入服务前的网络等待和Waitress排队** |
| 开启事务等待≥100ms、事务≥500ms或错误：读写类型、等待/事务耗时、错误类型/SQLite错误码、关联请求编号 | 定位写锁和慢事务；开启等待含连接建立及PRAGMA，不全部等价于锁等待 |
| Waitress队列/连接上限警告；持续异常时线程调用位置（最多每60秒） | 检查线程是否卡在数据库、业务锁或发送响应；不记录源码内容和局部变量 |
| 约30秒检查地址变化；服务循环退出、正常关闭 | 帮助对应重启、IP变化、假运行窗口 |

诊断不记录学生姓名、请求正文、Cookie、查询参数、密钥、SQL文本或完整学生IP；地址事件包含教师机局域网IP，日志请私下发送。旧application.log可能含异常上下文，发送前检查。当前未采集Windows磁盘延迟、完整网卡/路由、进程内存/优先级和浏览器网络事件，现场仍需要截图。健康接口只证明HTTP处理可用，不代表数据库健康；由数据库诊断共同判断。独立监测线程能报告部分卡顿，但整个进程被系统冻结或磁盘无法写入时仍可能无法留下日志。

## 4. 现场最小排查（约2分钟）

1. **先不要连续刷新或反复重启。**记下故障时间、学生机数量、正在选座还是签到；拍启动窗口状态和任务管理器CPU/内存/磁盘。
2. 教师浏览器打开`http://127.0.0.1:8765/health`（若改过端口，换为实际端口）。再在一台学生机打开`http://教师机IP:8765/health`。分别记录是否迅速出现`status: ok`、卡住还是立即连接失败。
3. 本机也慢：打开数据目录，复制`diagnostics.jsonl`及`.1`—`.4`、`application.log`及其滚动文件。记录是否有另一个数据库工具在编辑，是否有其他班级软件高负载。仅学生机慢：比较启动窗口IP和学生网址，检查教师机是否换网/无线、代理或安全软件拦截；不要直接关闭整个防火墙。
4. 保存日志后，关闭课堂程序一次，确认没有残留监听；重新启动一次，先测本机health，再测一台学生机，再逐步恢复全班。保留数据库、备份和配置，**不要删除数据或sqlite3-wal文件**。

可选由熟悉电脑的人在PowerShell查看：`Get-NetTCPConnection -LocalPort 8765 | Group-Object State`，以及`Get-NetTCPConnection -LocalPort 8765 -State Listen | Select-Object OwningProcess`。这是只读查询；没有结果不一定说明网络故障，也可能端口不同或程序已停止。

- 教师机Windows版本、CPU/内存、磁盘类型及任务管理器截图；是否安装实时防护/数据库查看工具。
- 学生浏览器版本、打开了几个页面/是否重复打开；教师机和学生机有线还是Wi-Fi、极域打开方式。
- 两端health结果、实际访问地址、错误文字（连接拒绝/超时/连接重置），教师端是否使用127.0.0.1。

## 6. 验证边界

- 旧150连接配置饱和复现成功，期间没有数据库压力。
- 外部写锁+12写请求受控复现成功，health排队，释放后恢复。
- 64个隔离Chromium页面完成64人登记与签到，持续轮询611秒；观察到最多261条连接，教师页面加载最大2.39秒，HTTP 5xx=0，JS错误=0。初次导航分16个并发批次，签到并发64；不是64台物理Win7电脑。该持续测试在学生方向调整前运行，方向调整另有浏览器回归。
- 原测试主要是64个HTTP客户端突发并发，加少数浏览器业务流程，**没有覆盖64台真实浏览器整节课持续轮询**。这次也仅单机约10分钟，不能当成40分钟机房验收，更不能宣称现场根因已全部修复。新版需现场再测一整节课。
